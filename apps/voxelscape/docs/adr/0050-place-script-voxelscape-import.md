# A model name is a string argument to a reserved "voxelscape" import

ADR 0046 gave a place script a bare, attribute-carrying import to name one of
the place's own attached models: `import zombie from "zombie" with { type:
"model" }`. ADR 0048 later gave `engine` itself a plainer answer to the same
underlying problem — reaching a host-provided capability without adding a
second module system to the interpreter — by making `"engine"` a specifier
`bundle.ts`'s own `require` shim resolves directly, rather than an ambient
declaration the bundler has to infer meaning from. This decision folds model
access into that same, simpler shape, and — since a script placing an NPC or
prop was always going to reach for whichever of these landed first — brings
the parked, never-merged `ScriptedNpc`/`ScriptedProp` classes in with it.

```ts
import { createNpc, createProp } from "voxelscape";

const npc = createNpc({ model: "zombie", id: "zombie-1", x: 0, z: 0 });
npc.move({ x: 5, z: 6 });
npc.die();

const rock = createProp({
  model: "rock",
  id: "rock-1",
  x: 10,
  z: 0,
  solid: true,
});
```

`createNpc` and `createProp` are plain factory functions, not classes: each
hands back a plain object closing over its own placement, never something a
script constructs with `new`. `model` is a plain string option, not an import
specifier — a string argument can never collide with a project file the way a
specifier can, so none of ADR 0046's bare-vs-relative reasoning applies here
at all. `id` is never generated by either function: every peer replaying the
same script must compute the exact same id independently (ADR 0026), so it
always has to come from the caller's own deterministic address, the way the
Zombies demo derives one from its population seed and spawn cell.

## Typing a model name against what the place actually carries

`voxelscape.d.ts` declares an empty `ModelsByName` interface and two
generic functions typed against it:

```ts
declare module "voxelscape" {
  interface ModelsByName {}
  function createNpc<K extends keyof ModelsByName>(
    options: CreateNpcOptions<K>,
  ): NpcHandle<ModelsByName[K]>;
}
```

A place's own attached models augment `ModelsByName` live, generated from
their actual bytes (`model-dts.ts`, unchanged in job from ADR 0046 — it
still turns a model's real part and motion names into literal unions, only
the block it emits changed shape); this app's own demo scripts augment it
with a small checked-in file per model they use
(`demo-scripts/zombie-model.d.ts`). Declaration merging is what makes both
additive: `createNpc("zombie")` narrows to the merged model's real type,
`createNpc("nope")` is a real type error naming the models that do exist, and
with no augmentation at all `keyof ModelsByName` is `never` and neither
function is callable. Checked directly against the real compiler
(`ts.createLanguageService`) before this shipped: two separate `declare
module "voxelscape" { interface ModelsByName { ... } }` blocks in different
program files merge exactly this way, the same base-file-plus-per-project-
augmentation split `engine.d.ts` already established.

A model name unknown to the place at run time — the type caught a typo, but
a script's own type can go stale after a model is removed — is a plain thrown
`Error`, caught the moment the call runs, not a `PlaceBundleError` at bundle
time: `bundle.ts` no longer inspects import specifiers to know which models
are "actually used," so there is nothing left for it to validate ahead of
time.

## Resolving "voxelscape" the way "engine" already resolves

`resolveSpecifier` gains `"voxelscape"` as a second reserved bare name.
Unlike `"engine"` — a magic string `__require` bridges to a live host object
at run time — `"voxelscape"` needs no runtime bridge: everything it provides
is either static hand-written source (`voxelscape-lib.ts`) or fully known
from the place's attached models at bundle time. So it resolves to an
ordinary synthetic module id, compiled once through the same
`transpileFile`/`__require` machinery as any project file — its own `import *
as engine from "engine"` resolves through the pre-existing `"engine"` case
with no new special-casing in `outputFor`. The synthetic module's source is
`voxelscape-lib.ts`'s hand-written `createNpc`/`createProp` text with one
generated table appended: `__models`, built from every model the place
attaches (unconditionally, mirroring `model-dts.ts`'s own "every attached
model, not just the ones some script imports" choice), so there is no
first-pass scan of every file's imports needed to know which models to
include.

## Considered options

- **Keep ADR 0046's per-model bare import, and add a separate
  `"scripted-figures"` import for `ScriptedNpc`/`ScriptedProp`.** This is
  what was actually built first, on this branch, before ADR 0048 landed on
  `main`. Rejected once ADR 0048 set precedent for something simpler: a
  reserved specifier the bundler itself resolves needs neither an import
  attribute nor a second reserved specifier — one function call to name a
  model plus one module to hold the placement functions covers both jobs a
  string argument can never collide with a project file the way a specifier
  can.
- **`ScriptedNpc`/`ScriptedProp` as classes, constructed with `new` from a
  model handle a separate `createModel` call returns.** This was the design
  the parked branch carried over. Rejected in favor of two plain factory
  functions taking the model's name directly: nothing about placing a figure
  needs constructor semantics, and a class-plus-separate-lookup step was
  one more moving piece than the actual job — turn an options object into a
  placed figure and a way to move or remove it — required.

## Consequences

- `bundle.ts`'s `importsOf` reverts to plain specifier collection; the
  `with { type: "model" }` attribute scanning ADR 0046 added is gone
  entirely, since a model name is no longer a specifier at all.
- `bundlePlaceProject` still takes the place's attached models as a third,
  defaulted parameter, unchanged from ADR 0046.
- Determinism (ADR 0026) holds the same way it did under ADR 0046: `models`
  bytes are a fixed, synchronous input already on `PlaceProject` before
  bundling starts, and decoding them into the `__models` table is a pure
  function of those bytes — two peers still produce byte-identical bundles.
- `ScriptedNpc`/`ScriptedProp` never merged to `main` under those names;
  nothing outside this decision's own branch ever depended on them.
