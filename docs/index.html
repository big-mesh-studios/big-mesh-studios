Writing a place for voxelscape

Writing a place

A place is a piece of the world with a script attached to it. This is how to write one, in six steps, from a single toast to a place that remembers you.

Every sample here is drawn from a demo place in this repository, trimmed to the part under discussion. Every function, effect, fact, and bound they use is listed in the reference, which is read out of the world’s own declarations and is the same artifact /place:docs opens in the world.

Your first place

A place is a piece of the world with a script attached to it. The script is ordinary JavaScript that runs in a sandbox, and it reaches the world through exactly one import. Everything this documentation describes hangs off that:

Opening the editor

Type /place:editor in the console. It is the same console every other command lives in — press Escape to close it. The editor is where scripts are written and where a place’s models are attached; this documentation is what the editor’s own language service checks a script against, so anything below that type-checks in the editor will type-check here.

What the sandbox gives you

The script has no DOM, no network, no filesystem, and no clock of its own. What it has is the voxelscape module and a shared clock every peer in the place agrees on. That is deliberate: two peers running the same script must reach the same answer, so anything that would let them disagree is absent rather than discouraged.

Reading and writing

Reading is a world query — a function in the module that answers a question about the running world, as a pure function of the clock and the replicated state. Writing is an effect — a call to dispatch naming a tag and a payload, which the trusted side validates and then applies.

Careful. Every effect and every fact has a fixed vocabulary, and the reference lists all of them with the bounds the trusted side enforces. A payload outside those bounds is dropped rather than clamped, so a script that dispatches an oversized fill does nothing at all — it does not fill part of the box.

Where to go next

A place that is only a toast is not much of a place. The guides below build one up in the order the world itself does: the terrain it stands on, the figures that walk it, the things a player sees, and the rules and data that make it a game.

The editor and the console

Two ways in, and they are not interchangeable. The editor is where a place is authored: its scripts, its models, its name. The console is where the running world is poked at, by whoever is holding the keyboard.

The editor

The script editor lists the files a place ships and lets you edit them with the same editor everything else in this project uses. Underneath, it runs a TypeScript language service over your scripts with the voxelscape module in scope — the same declaration this site’s reference is read from. That means completion, hover documentation, and an inline error all come from the world’s own types rather than from anything written here, and a script that type-checks in the editor is a script the world can run.

Attaching models

A place carries its own models: voxel figures published from rm-stacker and attached to this place. They are not imported by name into a script; they are attached to the place, and the editor generates a declaration from the attached files’ own bytes. createNpc then checks the model name you pass against exactly those, so a typo in a model name is a compile error rather than a figure that never appears.

Careful. The model name is checked at two different moments on purpose. At build time the name is checked against the models the place has attached; at run time it is checked against the models actually loaded, and an unknown one throws the moment the call runs. Attaching a model after a script is written is therefore safe, and removing one the script names is not.

The console

Press Escape for the console. Every command in the world is declared in one place and named for what the player has rather than what the code is built on, which is why the account commands are /account:*. A few are worth knowing while writing a place:

/place:demos and /place:demo <id> are the quickest way to see one of the built-in demos running. Those demos are ordinary place scripts in this repository, and every sample in these guides is drawn from one of them.

The reference, in the world

/place:docs opens the same reference this site serves, rendered from the same committed artifact. It is the whole vocabulary: every function, effect, fact, and bound. Having it open in a second window or on a second monitor while writing a script is the intended way to work — it is searchable, and it needs no connection to anything.

Terrain, with onPlan

Everything else in a place script happens during play. One thing does not: the terrain. A place’s terrain is built once, before the first fill, by a handler registered with onPlan. The world calls it exactly once, with the place’s seed and the region it may build in, and whatever plan string it returns becomes the land.

What it is given

The argument is a JSON string, not an object, because it crosses the sandbox boundary as text. It parses to a PlanContext: the seed the place’s world is generated from, and the region — a voxel box, inclusive at both corners — the plan may address. The return value is the same: a JSON string, parsing to a LevelPlan, or a bare array of shapes.

Seed from the context rather than from anything else. Every peer generating this place has the same seed, so a plan that uses it lays the same land in every peer’s world, and a plan that ignores it lays down whatever the local machine’s Math.random produced.

The six shapes

A plan is a list of plan shapes, and there are six. Each carries a kind and its own fields, and the reference draws every one of them:

  • box — an axis-aligned voxel box, the workhorse.
  • road — a flat strip between two points, for a path.
  • house — a box with wall, roof, and floor depths, so a building gets a shell and an interior in one shape.
  • stairs — a flight along one axis, with its own step, rise, and run.
  • ramp — a walkable slope between two points.
  • surface — a box skimmed with a different block, which is how a place gets a desert without becoming a different world.

Careful. A plan is in voxel coordinates; everything after it is in world feet. One voxel is two feet, so a plan coordinate is a world coordinate halved. Getting this wrong is the single most common way a place ends up floating in the sky or buried, and it is worth writing the conversion down at the top of the file — the demos do exactly that.

Shaping the same land after the fact

A plan is not the only way to build. The structure effect stamps the same shapes into the running world during play, which is how a demo builds a floor per run rather than per place, and block-set, block-fill, and block-clear move single voxels and boxes. A scripted block edit travels the same path a player’s own edit does — overlay, mesh, light, save, and broadcast — so it persists and reconciles exactly as a dug one does.

The level editor (/place:level-editor) is a third route: a place can ship voxel edits made by hand, the same ones a player would make, and they are loaded before the plan is asked for anything.

Figures and models

A place is inhabited by figures — the NPCs a script places, the props it sets down, and the players themselves. Every figure wears a voxel model, and the models a place may wear are the ones rm-stacker published and the editor attached to it.

Placing an NPC

The id is the one field that has no default, and it is not an oversight. Every peer in a place runs the same script against the same clock, so each must independently compute the identical id for the identical figure — a random one would place a different figure in every peer’s world. Derive it from something deterministic, the way the Zombies demo derives an id from its population seed and spawn cell.

Careful. createNpc throws if a model name is not one the place actually attaches. Omitting model entirely is not the same as an unknown one: the world draws its own default figure, exactly as a hand-written npc effect with no model does.

Standing figures in a plan

A plan may also stand figures among its shapes, so the land and its occupants are built in the same pass. Those take world feet, not voxels — the same coordinates a script’s npc effect takes, and the opposite of the shapes beside them. Both are written out in full in the reference.

The round trip through a fact is the pattern for anything a player does to a figure, and the reason a dialog handler keeps a little state: the script is told which option was chosen, not what the question was, so it has to remember where in the tree the conversation is.

Behaviours

A figure moves on its own only if a script tells it to. The entity-set effect sets a figure’s attributes and the figure-animate effect drives a motion, while zone marks out an area a figure acts within. The npc-remove and prop-remove effects take a figure away again, by the same id it was placed with.

Presentation

A place that changes nothing the player can see is a place nobody remembers. The presentation effects come in two families: the scripted interface, which a place builds out of named panels and items, and world dressing, the light and sound and weather that make the land feel like somewhere.

The HUD

A HUD readout is a line in a player’s overlay. It is named, so a later hud with the same id replaces it, and hud-remove takes it away. The empty player string means everyone locally, which is the usual case for a single-player place.

A bar needs a max; a text readout needs a text. Dispatch the same id every time the value changes rather than creating a new readout each time — a bar with a fresh id every tick is a bar the player watches multiply.

Panels, and what goes in them

Anything more than a readout is a panel: a docked box that items are added to. A panel is opened once by id, items are added and updated under that id, and ui-remove closes it.

The five item effects are ui-label, ui-bar, ui-button, ui-image, and ui-remove; every one takes the panel it belongs to, and every one is named so a later dispatch can update it in place. A button’s onClick is a tag, not a function: the sandbox has no way to call back into a script, so the click arrives as a fact and the script answers it on the next tick.

Light, sound, and weather

The land itself is dressed with the same vocabulary: createLight places a light and light-remove takes it away; createStorm sets the weather; createBillboard, createDecal, and createParticle add the scenery.

Careful. A sound names one of the world’s own fixed sounds, never a file or a URL — a place cannot ship audio of its own. The same goes for billboard images. id is required to loop, and a loop with nosound-stop left behind is a sound that plays until the place is left.

Talking to the player

Two smaller surfaces round it out. toast is a short message in the corner, for something that does not deserve a panel, and narrate is a line of prose for a moment that deserves one.

Rules and data

Everything so far has been a place that exists. This is the part that makes it a game: what a player has done, what it earned, and what the place remembers between visits.

Scoring

Scoring is a script’s own arithmetic. A strike arrives as a fact and the script decides what it is worth — there is no built-in score, because what a hit means differs from place to place.

A number kept per player under a key is what the world can rank across players, which is what a leaderboard is: player-value writes it, showLeaderboard displays it, and it should be written whenever it changes.

Teams

team-define declares the teams a place has and player-team puts a player on one. Teams are a name and a colour, and nothing more — what a team does is still the script’s, driven by the same facts.

Items

An item is declared with item-define, handed out with item-give, and taken with item-take. What happens when one is used arrives as an item-used fact, so the item is a name the world tracks and the meaning is the script’s.

Ending

Every ending a place defines is listed by getEndings, and ending is how one is reached for a player — a title and the text it ends on. restart puts them back at the start, and teleport sends them to another place, optionally carrying data across with it.

What a place remembers

A place remembers a data value — a string, a finite number, or a boolean — under a key, at one of three scopes. The scope is the whole decision:

  • player — one player’s own value, kept with them wherever they play the place.
  • global — one value shared by everyone in the place, for something a run changes for everybody at once.
  • account — one value for the signed-in account, readable across places.

A read is getData, a write is savePlayerData, saveGlobalData, or saveAccountData, and a deletion is deletePlayerData or deleteAccountData. A missing value reads as null rather than throwing, so a place can ask for something it has never written.

Careful. requestData is the asynchronous form: it asks the world to read, and the answer arrives as a data-loaded fact on a later tick rather than in the return value. Use it when the read is across the network and the script should not block; getData is the one that answers now.

Badges and the catalog

awardBadge awards a badge, remembered as that player’s place data, and comes back as a badge-earned fact so a place can mark the moment. openCatalog opens the world’s catalog — the search over published places a player enters a new one from — and teleport is how a script sends them there.

The reference is read out of the world's own sources by pnpm place-reference, so it cannot drift from the code it describes. Both are open source, in one repository: github.com/big-mesh-studios/big-mesh-studios.
